# 仓库架构与知识权威

本页定义仓库结构、知识归属、单向参数链和正式几何验收；操作见[操作指南](OPERATIONS.md)，产物与归档见[生命周期](LIFECYCLE.md)。

## 知识权威与写入路由

### 文档权威和冲突优先级

本仓库采用单一权威来源（Single Source of Truth, SSOT）。规范只在最高权威文档定义一次；下游
文档只链接该定义，并记录本项目的应用、例外或验证结果，不复制整段通用规则。

仓库使用者同时包括人类与AI。两者共享相同的项目入口、术语、机器契约和验收证据；不会为AI
另建一套内容不同的“简化真值”。`AGENTS.md`只额外规定Agent的执行行为，不取代面向所有使用者
的项目知识文档。

通用规则形成第二版本。

### 跨项目知识提升条件

先确定模型所有者，再确定可复用范围。部件局部理论和领域实现由该设计项目维护；其他项目通过
明确接口和引用复用，不因消费者增多而迁入公共层。正交加速器的二区／三区和多极杆的四／六／八极
都适用这一规则。整机联合模型归其仪器设计，跨组件执行和联合证据归integration。

只有不属于单一设计、具有独立使用边界的方法才提升到`docs/science/`或公共机制。数值与排错经验
须有不同设计场景的实测支持；两个目录、两个变体名称或同一实现的重复调用不能自动算独立验证。
没有相称复用证据的经验先留在原所有者，不通过更换存放位置提高适用范围。
有固定权威来源、明确符号和适用域的通用解析理论可标记`provisional`；建立求解器无关实现和
相称自动理论测试后才可提升为`reference`。这一成熟度与项目Candidate／Formal资格相互独立。

项目README提供统一入口，按实际需要指向状态、理论、实现、软件和历史正文，不要求每个项目拥有同样文件。
软件文档可直接引用共同实现或术语的唯一说明，避免复制或迫使读者绕回入口。当前状态始终只归PROJECT；
跨软件结论必须先统一输入并验证，再写入PROJECT。导航可以交叉，正文权威不能重复。
## 总体目录与项目边界

```text
simulation_repo/
├─ README.md          # 人和 Agent 共用入口
├─ AGENTS.md          # Agent 执行行为
├─ config/            # 自动生成的项目发现注册表
├─ projects/          # 独立器件或仪器项目
├─ integrations/      # 跨项目连接、编排和集成证据
├─ common/            # 已实际复用的机制与邻近说明
└─ docs/              # 全仓规则、science、tools、references及历史索引
```

项目测试留在各项目内；只有出现真正跨项目的仓库级门禁时才创建根 `tests/`，不预建空目录。

### 部件、实例与组装

“仿真组装厂”的使命见[愿景](VISION.md)，在目录中沿用项目、integration和公共机制的现有分工：

| 对象 | 所有者与边界 |
|---|---|
| 部件设计及其独立能力 | `projects/<project>/`；维护参数、几何、物理模型、提供接口及自身验证 |
| 部件实例 | 在组装配方中引用提供者并绑定实例配置与身份；不为每个实例复制项目 |
| 跨项目组装与联合研究 | `integrations/`；引用组件权威，维护连接、编排、联合证据与系统限制 |
| 可复用机制 | `common/`；按实际复用条件提升，不接管项目物理设计或科学结论 |

项目可以拥有完整分析器的物理设计，也可以拥有一个独立部件；“组装厂”不要求将现有项目按电极或
教材章节重新拆分。新增部件先检查已有设计、变体和工况能否表达需求；新增物理能力先明确模型与验证责任。
实例、端口、驱动、坐标、源和时钟的机器语义只由[连接架构](COMPONENT_CONNECTION_ARCHITECTURE.md)及其合同定义。
可发现、可布局、可运行与已验证是不同状态，项目和集成状态页各自记录，不由目录存在或愿景文字推定。

跨项目组装已批准收敛到仓库根`integrations/`的直属布局，组合以配方而非新项目表达；
目录与职责的唯一合同见[统一组装目标](COMPONENT_CONNECTION_ARCHITECTURE.md#统一组装目标)。实施状态见
[集成状态](../integrations/docs/INTEGRATION.md)，各活动路径按workflow完成验收后切换。
器件／仪器的物理设计与自身资格仍归项目，跨组件编排和联合证据归integration。

目录保持浅层，新增层级必须承载明确职责。项目、变体、workflow与文档专题可按实际边界分层，
不为每个器件、软件或阶段建立同构空模板；不再以目录数量或统一深度代替职责判断。
根`docs/science/`、`docs/tools/`与`docs/references/`分别承载公共方法、工具经验和外部来源。

### 项目与软件平权

每个 `projects/<project>/` 是一个可独立理解、验证和交付的研究项目。项目可以同时包含
`comsol/`、`simion/`、`cad/`、`analysis/`、`config/` 和 `tests/`，但不要求空目录占位。
目录按知识对象和生命周期划分，不按“主软件/辅助软件”划分。选择结果以物理问题和统一契约
为准，不以某个求解器先完成为准。

项目ID对应一个边界明确、可独立设计、验证和交付的硬件设计概念，不对应没有明确接口的宽泛设计族。
共享设计生成逻辑、接口语义和主要用途的结构变体由同一项目维护，例如正交脉冲加速器的二区／三区
以及RF多极杆的四／六／八极。根入口和项目README显式列出变体，不能合并成无法按杆数或结构查找的总页。
各变体必须显式区分参数合同、resolved几何、验证状态和资产身份；结构变体不是仅改变工况的mode，
也不能以一个变体的通过代替另一个变体的证据。设计族仍通过机器元数据和Roadmap关联。
同一硬件只改变电压、频率、气体、粒子源或运行目的时使用mode；不同科学问题可有独立workflow，
参数扫描和优化候选使用run。改变杆数或加速区数属于结构变体，不能混入电气mode。
当主要功能、接口或验收与发布生命周期需要独立演进时，建立新的平级项目；不只按电极数量拆分项目，
也不只因共享公式或family名称合并项目。双锥气流接口、离子处理器、电子枪和EI电离源各自维护独立设计。
项目统一不要求把实现拼成大文件：几何、驱动、分析、求解器适配和专用workflow仍按职责分开。
独立器件项目可通过显式版本化接口向多个仪器项目提供领域实现，不要求再复制到`common/`。
`common/`保留经不同项目实际复用验证的公共机制或没有独立器件项目归属的领域核心，不建立双份权威。

项目发现见根[README](../README.md#项目导航)和[生成注册表](../config/project_registry.json)。

每个项目用`config/project.json`声明稳定项目身份、设计族、可选择能力及其真实成熟度；
`common/contracts/build_project_registry.py`据此生成根`config/project_registry.json`。根注册表只用于
项目发现和自动选择，不取代项目`PROJECT.md`、baseline/resolved参数合同或Roadmap，也不得手改。
发生行政改名时，活动源码、新run和新artifact只使用当前`project_id`。描述符`legacy_identities`保留
旧项目身份及唯一artifact位置合同：未迁移时`source_pending_relocation`只读旧根，完成逐文件身份复核
后原子切为`archived_verified`且只指向当前项目的具名`archive/`载荷；不得长期回退或搜索旧顶层路径。
旧manifest不改写、不追加新run，并始终按其recorded project identity验证；行政改名、设计整合和路径迁移
均不得改变原资格、状态或声明边界。多项目整合须显式映射原项目到新项目的结构变体、配置与能力，
不能将多个旧资格合成一个无条件项目资格；在途运行继续按其冻结身份完成和交接。
## 参数权威与单向派生

所有项目必须遵循同一条不可逆的数据流：

`物理输入参数 + 公式 + 明确精度规则 → 项目config中的baseline工程参数 → resolved参数化简化 CAD 几何 → COMSOL / SIMION / GPT / CAD交付`

- `baseline`不是任一软件当前文件的抄录，而是物理输入经公式计算后的唯一工程参数契约。
- 公式、输入量、单位和工程舍入位数必须机器可读并接受门禁；不得只把最终尺寸散写在代码或文档中。
- `resolved`参数化简化 CAD 是跨求解器的唯一几何中间表示：它必须保留决定电场、束路和接口语义的
  电极、孔槽、曲线、间隙、屏蔽和检测面；螺钉、倒角、支撑等不改变该语义的工程细节可省略。它应由
  同一合同生成或驱动 CAD、COMSOL、SIMION 和 GPT 的各自输入，禁止在不同软件中手工重画近似几何。
- 原始/遗留 CAD 只能作为经审计的机械尺寸、曲线尺度、包络和制造约束证据。它不能反向定义物理拓扑、
  坐标、焦面、电压或 `baseline`；若与理论合同冲突，保留证据并以理论生成新的 `resolved` 几何。
- COMSOL、SIMION、GPT、CAD及SolidWorks只能读取、生成或验证baseline/resolved，不得因网格、格式化、
  GUI显示、旧模型或某个求解器的现有数值而反向改写它们。
- 求解器文件中的几何仅是一次性离散副本：PA/IOB、MPH、场图、网格、STEP或求解器私有对象可以为运行
  而保存，但必须能够从同一冻结`resolved`完整重建，且不得保存独有的可调几何参数、成为下次生成的
  输入，或接受人工 GUI 几何编辑。求解器只读地接受冻结输入，输出只记录实际消费的派生身份与结果。
- 扫描参数也必须先形成候选契约，再联动生成各实现；禁止分别手改多个软件后凭肉眼判断一致。
- 序列化精度不得低于baseline精度。`%g`、Excel显示位数或GUI四舍五入不能充当工程参数定义。
- 若实现与baseline冲突，实现一律判为失效候选；在重新生成、跨软件门禁和正式CAD同步全部通过前，
  不得转正。AI和人均无权为了迁就某一现有文件而擅自改变派生结果。

### 跨项目几何参数化标准

- 人工只维护`baseline`物理设计；项目解析器单向生成`resolved`，各软件不得重复推导或反写。
- `resolved`必须能导出可检查的简化 CAD，而不是只产生某一个求解器的私有脚本；各求解器的离散、
  网格和格式适配留在各自实现层，不得改变机械/物理几何语义。
- 数值模式与物理设计分层；候选运行参数不得反写物理baseline。
- 开发入口读取统一契约；SIMION等正式交付包可由该契约生成自包含文件，并接受过期门禁。
- 正式入口不得以缺失配置时回退到旧物理硬数字；候选覆盖不得反写baseline。
- 每项目提供`Static/Candidate/Formal`三级总门禁；正式几何仍须完成COMSOL GUI与SolidWorks同步。

## 语言职责

- MATLAB只负责COMSOL模型树、求解、GUI结果节点、MPH和正式STEP导出。
- GEM/Lua/Fly2只负责SIMION几何、PA/IOB、粒子和运行时行为。
- Python负责求解器无关的数据规范、峰形/FWHM/统计、跨软件比较和正式分析图。
- PowerShell只负责Windows环境检查、进程调用和PASS/FAIL门禁，不实现物理公式。
- JSON/CSV是跨语言机器契约；Excel只允许人工导入和检查，不能作为唯一真值。

分析算法不得在MATLAB、Python、Lua和Excel中平行发展多份。某项目建立Python参考实现后，
软件内MATLAB图表只作为GUI展示和对等检查；正式跨软件指标以项目`config/`中的版本化分析契约
和Python参考实现为准。公共Python代码仍须经过第二个项目实际复用后才能上移`common/`。
## GUI 与 CAD 门禁

- COMSOL：影响物理或数值结果的几何、选择、材料、物理场、粒子释放、网格、Study、Solver、
  数据集和派生值必须持久化为 Model Builder 中可见、可编辑、可保存的节点。必须重新打开 MPH，
  验证 GUI Compute 使用预期设置；只验证脚本 `runAll` 不足。
- SIMION：正式 IOB 的 PA 实例、坐标、电压、粒子定义和 Program 必须能在 GUI 中检查。关键
  物理不能只藏在命令行参数或外部后处理里；数值检测面也必须有 GUI 可见实体。
- 几何联动：迁移器件、间隙、电极厚度、孔径、屏蔽件和检测面尽量由统一参数派生。跨求解器
  测试必须证明坐标、有效面、粒子表和统计定义一致。
- SolidWorks：正式机械几何一旦确认，必须在同一任务更新正式 COMSOL MPH 和 SolidWorks
  零件/装配体，并验证数量、版本、变换、保存错误/警告和参数一致性；未同步不得称为正式完成。

## 文档维护与阅读体验

### 文档存放位置

先按知识所有者选位置，再按用途选文档；同一内容不因软件、Agent或一次对话重复保存。

| 内容 | 保存位置 | 留在入口中的内容 |
|---|---|---|
| 全仓使命、阶段及稳定规范 | 根`docs/`对应权威页 | 根README选任务，`docs/README.md`提供完整文档目录 |
| 跨设计科学与数值方法／工具经验 | 分别为`docs/science/`／`docs/tools/` | 任务目录链接专题，避免逐器件增加根级特例 |
| 项目当前事实与独立资格 | 项目`docs/PROJECT.md` | 项目README给用途、任务导航和特有前提 |
| 项目软件实现与命令 | 项目`docs/COMSOL.md`、`docs/SIMION.md`、`docs/CAD.md`，只建立实际使用的软件页 | 项目README统一导航，PROJECT只写跨软件结论及链接 |
| 项目专属推导、研究合同与发表材料 | 项目`docs/`既有专题目录 | 状态页链接，保留定义、假设和证据边界 |
| 跨组件当前状态与操作 | `integrations/docs/`及其工作流邻近说明 | integration README统一导航 |
| 公共代码API与使用方式 | 最邻近的`common/<domain>/README.md`；根级门禁和调度归`common/README.md` | 根文档不复制调用细节 |
| 学术参考书与论文 | `docs/references/literature/` | 书目、来源身份、适用主题及页码；PDF本地保留 |
| 供应商原始手册 | `docs/references/software/` | 软件版本、官方来源及定向章节；PDF本地保留 |
| 科学里程碑、旧方案与必要审计 | 所属`docs/history/` | 每个所有者维护唯一索引；根用AUDITS，项目或集成README链接其索引 |
| 普通编辑历史与重复全文 | Git固定提交及原路径 | 不因调整篇幅、链接或目录再复制全本快照 |
| 文档示意图与再生成脚本 | 正文附近的`figures/` | 图的假设、来源和复现入口；运行结果图仍归artifacts |
| 冻结输入、求解结果、模型和运行日志 | 仓库同级`artifacts/`的所属owner | 文档引用必要证据，不复制载荷 |

文档示意图可以随文进入Git；科学结果图、模型、粒子表和运行报告由所属run管理。
可维护历史索引与冻结正文分开，普通编辑由Git追溯；旧owner退役的处理见生命周期，不保留第二套活动项目入口。
外部原始资料不属于仓库自产技术结论；引用它们不绕过知识提升条件。
PDF本地保存和历史冻结的具体规则见[生命周期](LIFECYCLE.md#外部参考资料)。
新增独立文档应能回答现有页面不能清晰承载的问题；增加一个入口后应同步上级导航。
无需为每个项目建立同样数量的文档，也不为减少文件数合并具有独立假设、接口或验收责任的专题。

软件名称用于定位实现；章节按输入、运行、验证和故障组织。COMSOL通用指南负责选择路线，API页负责
调用语义，排错页负责症状到检查的路径；项目软件页只记录本项目接线。SIMION通用参考与公共实现README
同样区分工具行为和仓库API。CAD页保留格式中立名称，SolidWorks桥接细节归公共实现，避免把机械交付等同于单一软件。
跨软件共用的项目代码职责归`docs/IMPLEMENTATION.md`；同一流程不在几个软件页中重复。

### 内容与篇幅

规范说明应当如何工作，机器合同定义输入与接口，冻结证据证明实际验证范围。三者不一致时记录差异、
核对实现与来源；不得只按文档优先级改写物理事实、预注册门槛或历史结果。

| 内容 | 维护方式 |
|---|---|
| 项目入口 | 用途、按任务导航、可执行入口；不复制资格和运行结果 |
| PROJECT / INTEGRATION | 当前能力、合同入口、资格及证据、限制、开放动作与关闭条件 |
| 操作说明 | 工作目录、前提、显式输入、命令、输出和成功含义；标明商业执行和占位参数 |
| 理论 | 问题、符号与单位、假设、推导、适用域、原始来源、实现及验证入口 |
| 发表材料 | claim定义与来源归claim registry；证据状态归evidence matrix；研究计划不复制结果 |
| 通用经验 | 区分官方支持、项目实现和workaround，说明版本与实测范围 |

更新当前答案时替换失效叙述；只有达到[归档条件](LIFECYCLE.md#history-冻结条件)的科学或迁移记录才冻结，
普通文字修订和重复段落合并由Git保留。
每个事实只维护一个正文；参数表优先链接机器合同，派生展示必须注明来源且可重建。
新增文件先确认已有位置无法承载独立职责，不按每次对话、重试、软件阶段新建说明。
合并前检查代码、合同、历史和外部消费者；短迁移路由允许保留，不能包含第二份公式或状态。

正文使用中文叙述和稳定领域术语；代码标识保留原名。一个段落解释一个问题，操作用编号、比较用表格。
表格以结论和证据短链接为主，长路径、时间线及长解释放到正文或原证据。代码块标明语言；公式统一使用
GitHub可渲染的math围栏或行内数学。标题表达内容，避免用日期或不断增加编号组织当前状态。
长文提供任务目录；历史索引可用details折叠，但保留可检查的链接。既有冻结材料不批量改排版。

根入口约100–150行、项目入口约50–100行、状态页约150–250行是编辑参考，不是硬门禁。
超长、重复段落和宽表触发职责审查；独立推导、预注册合同和必要技术说明可保持合理篇幅。
常见任务应从项目入口两次导航内找到当前状态、机器合同、操作与证据；检查源码也要检查渲染结果。

### 按任务读取与局部检索

入口按“要回答的问题”指向正文的具体章节，并说明继续阅读的触发条件；不要把全部理论或软件手册
串成固定前置链。开发任务的必读集合由[开发标准阅读导航](DEVELOPMENT_STANDARDS.md#阅读导航)维护，
项目入口只增加本项目的前提。适用域、禁止路径和失败条件放在对应命令或结论之前，不能只在文末补充。

搜索命中是定位线索：采用某段指令前，读其所属章节的状态、适用域和权威引用。被取代内容不得在活动
正文中继续使用“当前”“任何下一步必须”等无时间限定的执行语气；按生命周期冻结旧过程，在原入口
明确给出替代路径。尚未发布的工作区能力应明示候选状态，不能仅靠有无链接、文件存在或排版区别表达。

理论保留定义、假设、推导和可证伪条件；研究计划维护实验矩阵；阶段合同维护进入/退出门槛；证据矩阵
维护当前通过状态。其他页面引用该正文，不再次抄写样本量、阶段结果或待办。表格缺项应写明“不适用”
及原因、明确待定边界或引用权威章节，不能用空白让读者猜测。修订时间点绑定相关合同或审查修订，避免
把“当前有未提交修改”作为长期项目事实。

文档升级的人工验收使用真实任务：只给入口和问题，复核读取者能否找到输入权威、当前资格、执行前提、
停止条件与验证入口；同时记录读取文件/章节和遗漏、误取旧指令的情况。优先修复错误答案和漏约束，再
减少无关阅读。链接可达、行数下降或结构门禁通过均不能单独证明知识一致性或科学资格。
