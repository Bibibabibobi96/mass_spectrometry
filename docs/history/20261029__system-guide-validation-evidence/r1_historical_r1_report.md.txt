## Whole dispatch reference and unresolved timing attribution

After the paired samples, the actual NEW dispatch loop consumes the same eight
live worker handles. This software fixture uses the shared GATE lease, stubs only
the solver-heavy assertion and system CPU/available-memory admission values, and
does not claim production admission/solver performance. Actual enumeration,
sampling, activity classification, WaitForExit/Dispose and loop sleeps run normally.

Four polls perform four Get-Process and four CIM enumerations. Whole wave:
57,098.3365 ms. Consecutive poll-start intervals: 1,895.7086 / 1,650.1308 /
52,342.6120 ms. Each active loop retains the original 500 ms sleep.

The third collector entry writes the stop sentinel; the long third-to-fourth
interval therefore includes that tiny write, actual enumeration, eight family
samples/activity/accounting, loop bookkeeping and 500 ms sleep. All eight
BATCH_COMPLETED console events occur in the final poll at ACTIVE=0 and about
57 s, so the long prior interval contains no reported completed-record event.
Ready waiting, GATE admission and the paired sample benchmark precede this loop.
The five-minute worker safety deadline is not reached. No sub-timers distinguish
CIM/property reads/other sampling statements, so the 52 s cannot be attributed
more precisely or explained away as the 500 ms sleep. It remains a visible
exit-transition cost in this fixture; this change claims no whole-scheduler gain.
