## G1：新增和修改的测试自身必须运行

生产匹配函数与真实 catalog 的探测确认：

| 唯一改动路径 | 当前选择 | 实际缺口 |
|---|---|---|
| MR `tests/analysis/test_simion_event_analysis.py` | MR Core | [Core 只运行四个固定模块](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/parallel_mirror_dual_stripe_mr_tof/verify_project.ps1#L38)，不含被改模块 |
| RF `tests/analysis/test_mass_filter_l1.py` | RF Freshness + quadrupole Core | [Core 在测试发现前返回](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/rf_multipole_ion_optics/verify_project.ps1#L74)，不运行该模块 |
| `common/contracts/test_expected_values.py` | common_contracts，精确 route 被覆盖 | 自身 4 tests 却触发完整 contracts 集合 |

这是**覆盖保证缺口**。Core/Static 分工是当前测试明确固化的设计，并非语法错误。也不能据此断言所有生产变更均未被任何 integration 测试覆盖。

最佳实现是在现有 catalog 给测试 owner 登记少量 `test_roots` 或等价元数据，把新增/修改测试的明确模块并入必跑集合，再与 Core 和必要合同测试合并去重。沿用 [现有 integration test-only 选择机制](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/verify_changed.ps1#L162)，避免每项目再写一个硬编码分支。

测试删除、重命名、共享 fixture、包初始化或无法映射的新目录，应扩大到适用 owner 的完整发现并报告原因。生产代码变化的反向依赖覆盖是另一件事：优先利用已有 runtime dependency inventory 与 owner 声明；无法证明安全缩小时保留 owner 回归。不能把“只跑同名 test”当依赖闭包，也无需一律把 L1 改为 Static。

验收必须使用真实入口：在临时工作树给 MR/RF 非 Core 模块加入确定失败的测试，L1 应返回非零并指出该模块；新增测试同样成立。修复测试后应通过。只检验 PlanOnly 的 stage 名称不足以证明实际测试已运行。

## G2/G4：先去掉无效工作，再减少必要检查的范围

[main 无条件 audit_consumers](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/verify_development_standards.py#L370)，即使未传 `--show-review` 仍执行；消费者分类不进入 hard errors，不改变退出码。它会在硬检查已解析全部 Python 后再次解析、反复遍历 AST。[pre-commit](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/.githooks/pre-commit#L25) 每次提交又运行完整标准，即使只修改文档。

第一步：把消费者审计放到显式 `--audit-consumers`、明确的 review 命令或 L2；默认保留真正决定 PASS/FAIL 的硬检查。输出 `NOT_REQUESTED`，不能把未扫描写成零候选。显式审计共享一次 AST/visitor 索引，无需增加逐文件 SHA 缓存。

第二步：L1/pre-commit 的硬检查支持明确路径；规则自身、配置、unknown 和 FullScope 变化仍全量，L2 保留全量。pre-commit 应检查实际暂存版本，不能用工作树中未暂存的修复证明索引内容正确。

第三步：修正 test-only 路由。`test_expected_values.py` 的精确选择不应先被 broad contracts route 吞掉。其本次单模块 0.095 秒、历史整组 293.799 秒是不同环境的证据，不能据此宣传倍速；但选择粒度明显不合理。缩小 unittest 集后仍可能因 `ruff_changed_python` 需要 locked 环境，不能承诺自动跳过依赖安装。

第四步：[PlanOnly 先按 selected 求环境等级](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/verify_changed.ps1#L388)，随后才缩小 DOCUMENTATION_ONLY 的 effective stages。项目 README 命中 locked route 时可能白装科学依赖。应先得出实际执行集，再求 dependency profile；验收覆盖根 README、项目 README、common/contracts README。此项尚未测 Windows CI 安装时间。

## G3：保留小摘要，明确每种终态

当前已经输出 RUN/PASS/ELAPSED_SECONDS、子进程完成信息和日志位置，失败组保留日志；不能说“完全没有计时”。问题在 [inline 与 child 分支](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/parallel_gate_support.ps1#L118)、异常收尾和 [成功日志清理](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/parallel_gate_support.ps1#L314) 之间缺统一的小结果对象，CI 也未统一 always 上传。

在既有 stage wrapper 的 finally 中生成结果，父进程写一份小 JSON，字段建议：阶段 ID、选择原因、命令参数、环境、开始/结束、排队/启动/执行/清理耗时、exit code、status、reason code、日志路径、测试数量与 skips（可获取时）。每个已选阶段都应出现；依赖失败为 BLOCKED，不适用为 NOT_APPLICABLE，不能与 unittest skip 混为一谈。成功长期保留小摘要，失败保留详细日志。摘要只是观测证据，不是跨改动跳过检查的资格令牌，因此不用给全库另算一遍 SHA。

最新历史写的是 37 阶段分别有通过证据，但完整命令 exit 1 保留；后续定向成功不能覆盖原命令失败。最终需要证明全轮成功时，在固定提交的独立 checkout 运行一次适用完整门禁，避免执行中编辑源码/文档。见 [本版验收记录](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/docs/history/20261028__unified-diagnostics-review-acceptance.md#L95)。

## 调度改法与小清理

L2 当前是文档 → 12 fast 全部完成 → 24 regression 的固定屏障；仅三个 RF stage 有显式前置。[队列按目录顺序启动](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/parallel_gate_support.ps1#L184)，组内发现非零后仍启动剩余任务，组末才统一失败。改用已有 catalog.requires_stages 形成 ready 集；必要短检查先跑，同优先级 ready 任务按可信历史中位耗时从长到短排，缺历史则回退确定性顺序。资源仍由现有 host scheduler 决定。

L1 默认在阻断失败后停止无独立诊断价值的待启动任务；L2 继续独立阶段以一次收集问题；依赖失败的后继立即 BLOCKED。已启动且健康的任务自然收尾，不为 fail-fast 误杀求解器。先对 MR/assembly 按测试模块计时，再按既有模块边界分片；不把所有套件强塞同一解释器，也不让子层绕过父预算再开池。

小清理包括 MR [对只有 Lua 文件的目录执行空 Python discover](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/parallel_mirror_dual_stripe_mr_tof/verify_project.ps1#L50)、同轮重复 Ruff/registry、重复 RF PowerShell 树解析、每组重新预热 Matplotlib。Ruff 本次全库仅约 0.11 秒，这些应排在真正热点之后，不值得另建复杂 pass-token 系统。三个纯 Lua 回归及其 fixture 消费者继续保留。

# 哈希与私有物化：让验证只发生在真实边界

## 现状与原则

接受“原则上不用哈希，必要例外说明理由”。它适用于状态判断、容量统计、路径选择、普通配置路由与同一保护期内重复读取。对于冻结科学输入、完整母 cohort、正式资产、跨 run 内容绑定与 cache generation，仍需明确内容身份，理由是防止错场、错源、错版本或复制不一致进入可复现实验。哈希只能证明字节指纹是否一致；没有签名与可信签名者时不能证明来源真实性，更不能代替物理检查、写隔离、权限或 owner/lease。

已有快路径应保留：[普通 cache materialization](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/simion/pa_family_cache.py#L4128) 已先 metadata；[snapshot_immutable_file](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/simion/cache_generation.py#L413) 复制一次、只核对目标完整摘要；[公共 writer CLI](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/write_run_manifest.py#L296) 已原子发布后只回读小 manifest；[consumer projection](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/verify_run_manifest.py#L87) 可只复核实际消费的记录。cooled frontend、single-reflection field plan、MR native freeze 已明确 metadata-only。不能再把这些已修正路径列为待取消整 PA 哈希的缺口。

| 边界 | 默认实现 | 例外与理由 |
|---|---|---|
| 内存参数、状态机、路径和角色合法性 | 类型、范围、Schema、显式条件，不用 SHA | 哈希无法证明物理或状态合法 |
| 日常容量、LRU、lease、布局 | 台账与必要元数据，不读 payload | 容量不是内容完整性证明 |
| 已封存 generation 的 probe/plan/selection | 小 manifest/receipt、名称/大小/对应关系 | 实际消费 owner 负责所消费字节 |
| 同进程、持续禁止写入/删除的 guard 内 | 复用已验证身份，不重复整读 | guard 释放、可写阶段、替换或异常后重新验证受影响部分 |
| 有 expected record 的私有复制 | 一次复制，目标完整核对，返回已验证 record | 源只作为复制输入时通常无需另整读源 SHA |
| 独立直接消费 immutable standalone | 首次核对所消费内容并持续 guard | 防止同名/同大小错误文件进入物理运行 |
| 新产物发布 | writer 建立一次完整记录、原子发布、小文档回读 | 真实跨发布边界，不能只凭存在或 mtime |
| 下游只消费某些历史结果 | 使用现有具名 consumer projection | 不扫未消费 PA/MPH，也不声称整个 run 完整 |
| 同次完整公共发布后 | 只检查小 manifest 的 status/project/mode | 删除重复全文 verifier |
| vendor 写入、保存、Fast Adjust | 明确私有工作区及结束后的必要验证 | 哈希无法阻止共享输入被写坏；不可用 hardlink 代替隔离 |
| 异常、修复、迁移、独立交付或显式深审 | 有范围、有原因、有计时的深检 | 必要全量验证保留，不能扩散到每个正常步骤 |

不用更弱摘要或 size/mtime 代替真正需要的内容身份。优先减少遍数、缩小消费范围、复用受保护的证明；不新增跨 run 的时间戳摘要缓存。

## H1：五次 SHA 的真实重复链

[Initialize-InstrumentIobPaCopies](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/integrations/workflows/single_reflection_flight/execute.ps1#L190) 依次 New-ShortPaCopy → Publish-ShortPaCopyDestination → Protect-ImmutablePaSource。公共实现正常无 mismatch 时，源完整 SHA 2 次、目标 3 次，另有 1 次复制；最终 run manifest 的绑定不在这五次内。

4 MiB 合成文件、真实 helper、三轮计数全部得到 source/destination/destination/source/destination：20 MiB 哈希读取加一次 4 MiB 复制；三个阶段合计 156.358、23.338、24.006 ms。首轮含 JIT，后两轮温缓存；有探针开销，使用 Linux 小文件分支。这证明重复遍历，不证明 Windows 大 PA 的实际加速倍数。

推荐把复制、首次校验、持久只读发布和后续读取保护交给同一 owner，由 publish 转交已持有的目标 guard 和身份，不释放后再开一个 registry 重新证明。当前 New 的目标验证用 buffered Get-FileHash，Publish 的大文件分支使用无缓冲读取；**必须先统一第一次权威目标校验的正确读取方式，再删除后续重复**。不能只删几行后验而退回已知不充分的读取策略。已有 expected manifest 时可进一步采用公共 snapshot 模式：目标一遍完整验证足以证明交付副本，源句柄负责防并发写入。

保留必要的独立字节副本、IOB 长期依赖和 Windows 写隔离。长 PA 公共入口已有真实历史验证，不能当成待重新研发的能力。published `.paN` 仍禁止供应商重开；需要的 standalone 从原构建期的新 PA 对象导出。权威说明见 [SIMION 长 PA 输入边界](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/docs/tools/SIMION_REFERENCE.md#L74)。

## H2：选择器和三工作点叠加读取

[响应选择](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/integrations/runtime/local_frontend_field_support.ps1#L194) 经 standalone_pa_family → [默认全 payload 校验](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/simion/standalone_pa_response_set.py#L407)；随后 New-Short 每个源/目标各 SHA，[每个 composition 后](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/integrations/runtime/local_frontend_field_support.ps1#L28) 又验证实际使用输入，末尾另一 registry 再验证原源。

设选中 N 个响应、三个工作点各使用集合 U_j，典型冷路径 SHA 次数为 `4*N + sum(len(U_j))`，不含小 JSON 与新输出。各工作点使用项不同，不能粗略写固定 7N。

选择器只验证已封存记录及响应/网格/名称绑定；载荷证明归实际消费 owner。[composer](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/simion/compose_standalone_pa.lua#L75) 创建新输出、只读源，可优先评估通过既有 Protect-ImmutablePaSource 直接受护读取 standalone。若具体消费者仍需短副本，就让目标在全部 jobs 内保持 readonly guard，每个 job 后只查状态/句柄，不再整读。不能用 `verified=true` 布尔值跨进程冒充证明，也不能跳过小 receipt 身份检查。

这个改动需要一次最小真实 Windows/SIMION composer 回归：长路径、持续只读 guard、三个工作点、新输出、源不变、物理结果一致。它是已有直接读取能力在此消费者上的验证，不是重开长路径研发项目。

## H4/H5：布局深审与小输入冻结

[verify_common_pa_family_cache](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/verify_artifact_layout.py#L880) 无条件调用默认 full-payload 验证；[main](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/verify_artifact_layout.py#L1025) 在 project/formal-only 选择前先查整个 artifacts root。因此即使不带 verify-hashes，仍可能全读 common PA current generations。OPERATIONS 已声明这个例外；它不是默认 GitHub CI 的慢项。

建议默认 layout 只查布局、owner、pointer、manifest 关系、大小、只读及 lease 等必要元数据，把 verify-hashes 传给 cache 校验，显式深审才读全部字节。project/formal-only 不应隐式深审无关 global payload。输出验证 scope、文件数、hashed_bytes、elapsed；深审入口仍保留。

[Copy-VerifiedRunInput](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/run_artifact_support.ps1#L729) 正常路径 source-before/source-after/destination 三 SHA；[portable closure](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/rf_multipole_ion_optics/runtime/analysis_run_lifecycle.ps1#L4) 先验证源，再调用它，随后 [验证新 closure](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/rf_multipole_ion_optics/workflows/same_solver_convergence/run_comparison.ps1#L175)，典型独立记录达到源 3 次、目标 2 次。多数是 JSON、源码、粒子 CSV 与库存，并非重复整份 MPH/PA。共用 record-bound copy：已有期望记录，复制一次、目标验证一次、返回身份；路径改写与角色选择留给原 workflow。先量化 CSV 规模再决定优先级。

不默认改成 Python 流式边复制边 SHA。Python 3.11 官方 [shutil 文档](https://docs.python.org/3.11/library/shutil.html)说明平台可能使用高效复制路径；合并循环减少遍数，也可能放弃平台优化。Windows 大文件应在相同输入与 I/O 条件下比较，继续复用现有无缓冲实现。

# 容量控制：日常准入合理，维护和自动收尾需要补齐

## 已有自动化值得保留

[公共 run 创建](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/run_artifact_support.ps1#L608) 已自动登记 writing range；[容量 session](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/run_artifact_support.ps1#L154) 创建 lease、保护输入、检查剩余新增承诺；预算增长会重新准入；[终态 manifest](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/run_artifact_support.ps1#L312) 按条件自动 finalize-ready；PA owner 在发布、复用、回滚时更新台账；项目已有 GUI/重载荷 seal；finally 释放 lease。进入 maintenance 后已自动串联八类 owner continuation，并隔离单 owner/对象失败。

正常 startup 已是 ledger-only，不遍历所有 artifact，不读取 PA payload。账本范围验证也已用路径前缀集合，不再是旧版两两范围比较。当前策略集中在 [容量 policy](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/artifact_capacity_policy.json)：受管目标 700 GiB、物理空闲底线 295 GiB，是当前工作站政策；没有实际磁盘与峰值数据，不能凭代码审查调整这些数值。性能目标/告警不应变成新的安全失败条件。

## C1：维护中的 O(R×N) 空转

[resume_partial_retirements](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/run_capacity_lifecycle.py#L762) 先收集所有 run，对每 run 调 [_eligible_partial_entries](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/run_capacity_lifecycle.py#L707) 再扫整个 ledger；无匹配时又扫一轮。全过程持有容量决策锁。旧式逐文件 ledger 的合成 no-op 实测：100/300/600 条、各属不同 run、全部 ready/light、无载荷且无可删对象，分别 0.060/0.524/2.107 秒，删除均为 0。

这是此 owner 在特定账本形态的二次成本，不代表正常新 run 的 startup 都有同样问题。修改为一次构造 by_run/by_path，并预筛可进入本 owner 的状态；每 run 只看所属记录。先消除重复扫描，再根据实测决定锁能否缩到单 run 事务。固定 pending receipt、删除前身份、lease 和下游消费者检查继续保留。

验收重点是访问次数随 N+R 近线性、无可操作对象不做 payload I/O、pending 重放不重复记账/删除、保护登记不会被无效历史扫描长期阻塞。不要为这条问题迁移整个账本数据库。

## C2：总时间漏掉 owner 维护阶段，结果也漏一类

[main](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/reconcile_artifact_capacity.py#L1565) 先执行八类 owner action，再创建 plan/apply 计时。注入 owner 延迟 0.25 秒后，实际 wall 0.251812 秒，receipt `timing.total_seconds` 仅 0.000616 秒。[结果拼装](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/reconcile_artifact_capacity.py#L1610) 还遗漏 partial_run_retirement；注入 completed=3、removed_bytes=123456、blocked=2，最终 JSON 没有这些值。

在 CLI 入口建立唯一总计时，每个现有 owner 返回 status、elapsed、计数、error code 和 receipt 路径，统一序列化 owner_actions，停止用逐项 if 手写拼装。保留紧凑默认输出，详细逐对象证据留在既有收据。分别报告 `capacity_satisfied` 与 `closure_complete`：空间足够不等于所有生命周期问题都解决。

## C3：正常准入很快，但同 CLI 可以少算一遍

直接 Python API、Linux 温缓存、合法合成元数据，100/1,000/10,000 条 ledger 三次中位分别 0.001273/0.008583/0.086903 秒。它不含 PowerShell、Python 新进程、Windows 主机观测和排队，不能宣称真实端到端启动小于 0.1 秒。

标准 wrapper 总传 startup --apply；[apply](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/reconcile_artifact_capacity.py#L1274) 又重新执行 startup gate，实计 ledger/lease 均加载 2 次。同 CLI 可直接执行一次最终准入；独立 plan、过一段时间再 apply 的重检保留，避免期间新增承诺被忽略。前者是可省的重复，后者是实际并发边界。

## 自动闭环的最佳边界

源码未找到统一周期维护调度配置；这不证明真实工作站没有仓库外计划任务。优先改为容量压力触发：仅当明确空间缺口时，公共入口在当前有效输入保护 lease 保持/续期的前提下，尝试一次既有授权范围内的 maintenance，然后重新准入；不能先走失败 catch 释放当前输入保护，再执行清理。账本损坏或当前请求的输入身份冲突直接报告具体错误，不盲目重试。没有 owner/manager/处置证据的历史对象保留并报告原因，继续处理独立的已授权对象；历史待决项本身不能自动升级为当前启动阻断。不要让每次新 run 都重维护，也不需要先建常驻服务。

[SelectedHeavyPaths 子集退役](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/contracts/invoke_solver_review_retirement.ps1#L100) 目前提示 Agent 手工 reseal。原 owner、保留理由、pin 已明确时应自动接上；seal 失败只恢复 seal，不重复删除或求解。新流程从创建、运行、保留、manifest、ledger seal 到 release 由现有 owner 连成一次调用；跨 run 恢复仍创建新 run 身份，不能改写历史终态。

历史 checkpoint、未知用途、唯一证据或尚在使用的 GUI 文件不能靠通用层猜测科学状态。自动化应减少手动搬运事实，不能消除必要的 owner 决定。TTL 过期、failed/interrupted、低 CPU、文件年龄均不能单独成为删除授权。容量 lease 与主机资源 lease 保护不同约束，仍应分开。

# 并行与耗时：在现有资源预算内按工作量调度

## R1：每轮采一次系统快照

[worker 循环](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/resource_budget_support.ps1#L990) 对每个 running worker 调 Get-ManagedSolverProcessSample；该函数分别 [Get-Process](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/resource_budget_support.ps1#L116) 与 [Win32_Process CIM](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/resource_budget_support.ps1#L161) 全机枚举，每轮末休眠 500 ms，实际周期还包含采样与调度开销。W 个 worker 每轮约 W 组系统快照，是明确的调用倍增；本审查未测 Windows CIM 毫秒数，不能承诺 W 倍提速。

每轮建立一份父子图、PID 创建身份、CPU/内存快照，再对各 launch 投影 owned process tree。保留 PID 复用、launcher 已退出但后代仍存活、conhost 与不可读身份规则，不跨轮沿用旧快照判断进程安全。验收 1/4/8 workers 时每轮全机枚举均为一组，并测 poll_elapsed_ms。目录不能再把旧版“每 500 ms 扫目录”列为现状。容量递归采样当前已移到约 30 秒，

## heavy 互斥应有条件放宽

[准入策略](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/host_resource_scheduler.py#L226) 在 CPU/内存判定前阻止第二个 heavy；[heavy-compute/simion-flight](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/host_resource_policy.json#L38) 的 CPU 和 memory 预算为 0，代表交给内部调度，不是零成本。直接删互斥会让多个内部 planner 各自按整机余量扩张。

应保留尚未受中央正预算约束、内部可自适应扩张的重任务独占；未知峰值本身不应升级成 heavy。对已测量的独立 case 先声明并实际约束正 CPU/内存预算，再交同一中央调度。已有 simion-dirichlet-response 的 2 核、6 GiB、非 heavy 模式是可沿用路径。GUI、许可证或共享模型仅在真实冲突时保留 exclusive_resources。不给每项目新增调度器。

## 按时间均衡，而不只是按粒子数

现有 [case planner](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/simion/resource_scheduler.py#L647) 已考虑资源，独立粒子也已有分批与完整合并。下一步先记录 queue、prepare、PA load、compute、postprocess 的实际时间，按可信历史估算长任务优先并保留 aging；缺历史时用现有确定性顺序。粒子拆得越碎，PA 加载与进程启动可能越多，不能只追求均匀 N。

可并行的候选包括独立测试模块、独立场响应、不同候选 case、给定外场下独立粒子批次、互不依赖的后处理。空间电荷、离子间相互作用或共同场反馈不能把粒子独立拆批；这不限制求解器自身支持的并行。单盘大文件哈希/复制也不按 CPU 核数盲开 workers，应先消除重复读，再按 I/O、内存、工作量设有界并行。

并行不改变母 cohort、原粒子 ID、输入、种子策略、clock、网格、时间步、精度与终止条件。合并必须恰好覆盖声明粒子并保留上游损失。科学失败不自动重试；健康已运行任务不因另一个失败被强杀。

不建议现在引入常驻 daemon、复杂性能预测服务或第二套任务数据库。[主机 transaction](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/common/host_execution_lease.ps1#L301) 的进程枚举、Python 启动、SQLite 锁等应先分项测量；只有实测证实后，才考虑在原 controller 内批量查询。Python CPU 计算若最终确需进程池，可参考 Python 3.11 官方 [concurrent.futures](https://docs.python.org/3.11/library/concurrent.futures.html)，但不得与现有 host/solver 内层并行重复承诺资源。

# 架构与语言职责

## 目标依赖关系

沿用仓库既有项目中心组织：common 拥有中性机制和求解器无关的公共诊断；项目拥有器件物理、阈值、科学决策和资格；integrations 拥有组件装配与整链编排。跨项目部件 API 复用本身合理，不因出现多处引用就把器件模型搬进 common。规则依据 [语言职责](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/docs/REPOSITORY_ARCHITECTURE.md#L196) 与 [共享依赖方向](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/docs/DEVELOPMENT_STANDARDS.md#L111)。

```mermaid
flowchart TD
  W["现有 workflow 入口"] --> I["integrations 装配与编排"]
  W --> P["项目物理与科学决策"]
  I --> P
  I --> C["common 合同与生命周期"]
  P --> D["common 纯诊断与数值原语"]
  P --> C
  I --> V["供应商适配与进程入口"]
  V --> C
```

| 语言 | 最合适的职责 | 本次建议 |
|---|---|---|
| Python | 合同编译、纯物理/数值决策、canonical 状态/峰形诊断、统计、计划与结果聚合 | 保持科学权威；项目阈值不移公共层 |
| PowerShell | Windows/进程/许可证与环境接入、公共资源与容量会话、路径和门禁编排 | 执行计划与转交结果，不平行维护科学分支 |
| MATLAB/COMSOL | 供应商模型树、网格/Study/Solver、LiveLink 生命周期、原始输出转换 | 不为统一语言搬到 Python；提取清楚的供应商阶段 |
| Lua/GEM/Fly2 | SIMION 几何/回调/粒子运行、实际事件记录与必要字段转换 | 不承担第二份通用 FWHM、分辨率和资格解释 |
| JSON/Schema | 唯一科学/数值/运行权威及显式派生关系 | 不把日志、回执和显示名变成第二份参数权威 |

## A1：MR 控制器仍横跨 PowerShell 与 Python

[3,205 行 runner](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/parallel_mirror_dual_stripe_mr_tof/analysis/run_downstream_workpoint_iteration.ps1) 与 [2,911 行 controller](https://github.com/Bibibabibobi96/mass_spectrometry/blob/3005980a9a0d3a62a67f36dff389a3110868faa7/projects/parallel_mirror_dual_stripe_mr_tof/analysis/downstream_workpoint_iteration.py) 并存本身不是问题；问题是同一科学决策仍分散。

# 面向 Agent 的最小执行合同

推荐在现有入口、run summary 和 stage receipt 上统一少量字段，不新增第二套工作流平台。一次正式请求应完成可以确定的“轻量解析/计划 → admission → materialize/prepare → execute → collect → analyze → retain → manifest → capacity-seal → release”。大 PA 物化、复制和其他重写入必须在容量/资源准入之后；前置解析只生成必要的轻量计划。运行中的正常进度可输出事件；最终一定有明确终态。GUI 或科学决策确需用户/owner 输入时，停在具名边界并给出已完成结果与精确缺项。

```json
{
  "status": "failed",
  "stage": "capacity_seal",
  "error_code": "OWNER_CLOSEOUT_INCOMPLETE",
  "reason": "已发布计算结果，保留载荷的 owner 收尾未完成",
  "last_completed_stage": "manifest_publish",
  "resume_action": "继续原 owner 的容量 seal；复用已发布计算结果",
  "elapsed_seconds": 12.3,
  "timing": {"queue": 0.8, "prepare": 1.1, "compute": 8.0, "publish": 2.4},
  "evidence": {"manifest": "run_manifest.json", "log": "logs/stage.log"}
}
```

上例是建议形状，数字为示例，不是本次运行结果。实际字段应沿用已有名称，避免同义字段。运行状态、科学判定、容量收尾分别表达：进程执行成功不等于物理假设成立；科学负结果不能被清理器改成成功；已发布科学终态不能因后续容量失败被覆写。

计时至少分 wall/queue/prepare/compute/postprocess/publish/cleanup；涉及大文件时增加 bytes_read、bytes_copied、bytes_hashed、hash_passes。用单调时钟计算耗时，UTC 时间戳用于定位。所有失败也写耗时与 failed stage。只在负责该边界的位置增加信息，不为每个小 helper 建状态机。

恢复应自动识别完成单元并显示理由。已有完整原始结果就只重跑后处理/发布，已成功场单元不因飞行失败重新 Refine；完整批次复用，未完成批次整体重跑。跨 run 恢复建立新 run_id、明确绑定父证据，不重新搜索 latest、不改旧终态、不隐式换输入。调度 hint 和耗时记录不进入科学内容身份。

**最关键的 Agent 收益指标**：一次请求需要人工续步次数、失败后需要读取的文件数、恢复时重复计算/复制字节、同一事实重复验证次数、阶段选择可解释性、失败到可复现命令的距离。代码行数与脚本数作为变更报告附带统计，不能替代这些指标。

# 推荐实施顺序与完成判据

## 第一批：正确覆盖、完整观测、无需改变物理行为的省事修改

G1 changed-test 必跑与 G4 test-only/effective 计划一并修；G2 把 advisory 从热路径移出；G3 统一阶段摘要；C2 补 owner 总计时和 partial 输出；C1 建一次索引；C3 消除同 CLI 重复 startup。顺带删除已确认无消费者的 Test-PathPrefix 和空 Python discover。工作边界都在现有 gate/capacity 实现，不增加新控制平台。

完成判据：确定失败的改动测试必能使正式 L1 失败；文档计划的 dependency profile 与 actual effective 集一致；成功/失败/启动失败/中断均有阶段结果；owner 注入时间计入 total；partial 结果完整；no-op 遍历近线性；现有保护与 pending 重放回归保持。性能比较报告测试范围，不能用少跑必需测试制造更快。

## 第二批：统一发布与验证 owner，减少真实大 I/O

先完成 H3 的完整 Python publisher 与私有发布迁移；然后 H1/H2 的 guard 连续转交、一次权威校验；再 H4 的显式深审和 H5 record-bound copy。不要同时改物理参数、缓存科学 key 或供应商输入表示。已有 cache_generation、file_identity、short_pa_path_support 是唯一实现归属。

完成判据：缺失输出、错误期望 SHA、同长度错误目标、guard 失效、异常 cleanup 都有最小行为测试；同一受保护链不再重复整读同一 payload；源和私有目标不共用可写文件对象；输出 hash/copy bytes 与次数可审计。影响 Windows 大文件读法或 SIMION composer 接入时，再执行相称真实最小回归；不要求不相关模型重跑。

## 第三批：少手工续步、预算内并行

自动接上已确定 owner 的 retire→reseal、容量压力 maintenance→再准入；R1 单轮共享快照；gate ready 队列和时间排序；对已测量独立 case 声明正预算后扩大并发。先测模块长尾再拆门禁阶段，保留独立诊断与进程隔离。

完成判据：每个断点可仅恢复未完成部分，不重算已有结果、不重复删除、不改旧科学终态；依赖失败不启动后继；L2 继续独立阶段；并发承诺不超 CPU/内存/I/O/许可证；PID 与后代安全回归保持。真实同 workload 墙钟改善才可声称提速。

## 第四批：逐个职责边界重构与退役

优先 A1 的 Python 科学决策归一，A2 的实际反向依赖，以及 long-file 附录中的热点。每次只切一个可验证职责，原入口保持唯一，替换完成即删除旧分支与失效参数。保留稳定的理论模块、生成合同和有价值的失败测试。不以“每文件少于 600 行”或“减少某个百分比代码量”作为完成标准。

不要为了本审查先建全仓新类型层、替换测试框架、引入守护服务、增加更多 SHA 或全仓 formatter。这些没有当前证据支持。最好的下一轮成果应当是：必需验证更可靠、普通流程更快、一次运行给出完整答案，Agent 不再依靠阅读多份日志和手动续命令才能判断系统状态。
